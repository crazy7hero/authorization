# 国密授权管理系统 — 设计文档

> 本文档面向接手维护的开发者，解释整个授权系统的设计思路、核心算法和关键决策点，让新人能快速理解"为什么要这么做"而不是"代码写了什么"。

---

## 1. 项目概述

### 1.1 定位

一个基于**国密算法（SM2/SM3/SM4）** 的软件授权管理工具。用于生成和验证软件授权文件（`.lic`），将授权与具体计算机硬件绑定，防止授权被复制到其他机器使用。

### 1.2 技术栈

| 组件 | 选择 | 说明 |
|------|------|------|
| 框架 | Qt 5.15 + MinGW | 跨平台 GUI 框架 |
| 加密库 | GmSSL 3.x | 国密算法实现（SM2/SM3/SM4） |
| 授权文件格式 | JSON + Base64 | 二进制字段以 Base64 编码后嵌入 JSON |
| 跨平台 | Windows / Linux  | `machine_id.cpp` 三套实现 |

### 1.3 核心文件一览

| 文件 | 职责 |
|------|------|
| `machine_id.cpp/.h` | 采集硬件信息，生成机器指纹 |
| `gmsslcrypto.cpp/.h` | 封装 GmSSL 的 SM2/SM3/SM4 操作 |
| `licensegenerator.cpp/.h` | 生成授权文件（核心业务） |
| `licensevalidator.cpp/.h` | 验证授权文件（核心业务） |
| `configmanager.cpp/.h` | 配置文件读取（config.ini） |
| `mainwindow.cpp/.h` | Qt 界面 + 交互逻辑 |
| `licensemanager.pro` | 编译配置，含宏开关 |

## 2. 机器码生成规则

> 对应源码：`machine_id.cpp`

### 2.1 设计目标

- 同一台机器每次生成的 ID **稳定不变**
- 不同机器生成的 ID **互不相同**
- 虚拟机/容器中能够识别并做特殊处理
- 硬件更换部分组件时 ID 尽量保持稳定

### 2.2 硬件信息采集源

根据平台不同，采集以下硬件标识：

| 平台 | 采集项 | 来源 |
|------|--------|------|
| Windows | MachineGuid | `HKLM\\SOFTWARE\\Microsoft\\Cryptography\\MachineGuid` |
| | CPU ProcessorId | WMI `Win32_Processor.ProcessorId` |
| | 主板序列号 | WMI `Win32_BaseBoard.SerialNumber` |
| | 硬盘序列号 | WMI `Win32_PhysicalMedia.SerialNumber` |
| | MAC 地址（物理网卡） | `GetAdaptersInfo` API |
| Linux | machine-id | `/etc/machine-id` 或 `/var/lib/dbus/machine-id` |
| | 主板 UUID | `/sys/class/dmi/id/product_uuid` |
| | 主板序列号 | `/sys/class/dmi/id/board_serial` |
| | CPU 序列号 | `/proc/cpuinfo` 中的 Serial |
| | 硬盘序列号 | `/sys/block/{sda|nvme0n1|hda|vda}/device/serial` |
| | MAC 地址（物理网卡） | `getifaddrs` + AF_PACKET |
| | hostid | `gethostid()` |
| | 容器内 | 额外尝试读取宿主机 `/host/etc/machine-id` |


### 2.3 原始数据过滤规则（`IsValidHardwareId`）

采集到的每条原始数据经过以下过滤，不合格的丢弃：

- 长度 < 4 的丢弃
- 内容为占位符的丢弃：`"To be filled"`、`"O.E.M"`、`"Default"`、`"None"`、`"Unknown"`、`"Not Available"`
- 全零的丢弃（全 0、全 `0:`、全 `0-`）

### 2.4 MAC 地址采集过滤规则

采集 MAC 地址时会跳过以下虚拟/非物理网卡：

- **Windows**：名称含 Virtual、VMware、Hyper-V、VirtualBox、Bluetooth、PPP、VPN、TAP、Tunnel、Loopback、vEthernet、Docker
- **Linux**：接口名含 lo、docker、veth、br-、virbr、lxc、nflog、nfqueue、tun、tap

- 全零 MAC 地址直接跳过
- **取第一个有效的物理网卡 MAC**

### 2.5 组合算法

原始ID = component1 + "|" + component2 + "|" + ...（去重后用 | 拼接）
哈希ID = SHA256(原始ID) → 64 位十六进制小写字符串

步骤：
1. 调用 `CollectHardwareComponents()` 收集所有平台的硬件标识
2. 对每条标识执行 `IsValidHardwareId()` 过滤
3. 去重（`std::set`）
4. 用 `|` 拼接所有有效标识
5. SHA256 哈希

### 2.6 有效性判定与 fallback

**`IsValid()`**：有效硬件组件数 >= 2 才算合法。

如果 `CollectHardwareComponents()` 返回空（极端情况，如权限不足），则回退到持久化 fallback 机制：

- **Windows**：保存到注册表 `HKCU\\Software\\MachineId\\HardwareId`
- **Linux**：保存到 `/var/lib/machine_id`
- fallback ID 格式：`fallback-{UUID}`

> 注意：fallback 机制生成的 ID **不能在多台机器间保证唯一性**，仅作为最后的容错手段。正常情况不应触发。

### 2.7 虚拟机检测（`IsRunningInVM`）

通过以下特征判断是否在虚拟机中：

- **Windows**：WMI 查询制造商和型号，匹配 VMWare、VirtualBox、Hyper-V、QEMU
- **Linux**：读取 DMI 信息（sys_vendor、product_name），匹配 VMWare、VirtualBox、QEMU、KVM、Microsoft；同时检测 `/proc/cpuinfo` 中是否有 `hypervisor` 标识

## 3. 密钥管理
> 对应源码：`gmsslcrypto.cpp/.h`、`licensegenerator.cpp`

### 3.1 生成的三份密钥文件

执行一次"生成密钥"操作产生三个文件：

| 文件 | 算法 | 格式 | 用途 |
|------|------|------|------|
| `sm2_private.pem` | SM2 私钥 | PEM（可加密） | 授权签名（生成端持有，需保密） |
| `sm2_public.pem` | SM2 公钥 | PEM | 授权验签（可嵌入应用，公开） |
| `sm4_key.bin` | SM4 密钥 | 16字节 hex → Base64 | 授权数据加密（生成端和客户端共享） |

### 3.2 SM2 私钥保护

SM2 私钥在导出 PEM 时使用密码加密保护：

```cpp
#define SM2_SIGNI_KEY_PASSWORD "123456781234578"
```

- 该密码定义在 `gmsslcrypto.h` 中
- 字段含义：SM2 签名密钥的加密口令
- 当前硬编码为固定值，便于开发和测试阶段使用
- **生产环境中应更换为更强的密码**，或改为从配置文件读取

界面中密码输入框已被隐藏（`mainwindow.cpp` 构造函数中 `setVisible(false)`），因为当前所有密钥统一使用同一个固定密码。

### 3.3 SM4 密钥存储格式说明

SM4 密钥在文件中的存储方式经历了**两次编码**：

原始SM4密钥（16字节二进制）→ toHex() → 32字符十六进制字符串 → toUtf8().toBase64() → Base64 编码 → 写入文件（纯文本内容）

读取时反向操作：

Base64解码 → 得到十六进制字符串 → fromHex() → 16字节密钥

> 注意：`sm4_key.bin` 虽然是 `.bin` 后缀，实际内容是 Base64 文本，不是原始二进制。这么做的意图是让文件内容为纯文本，便于人工查看。

## 4. 授权码生成流程

> 对应源码：`licensegenerator.cpp` 中的 `generateLicenseWithHashAndSign`（V2，当前默认）

### 4.1 整体流程图

```
┌─────────────────────────────────────────────────────┐
│                   生成端                              │
│                                                       │
│  授权数据(JSON) ──→ SM3哈希 ──→ SM2签名              │
│                      │                    │           │
│                      │               ┌────┘           │
│                      ▼               ▼                │
│              哈希值 + SM2签名 组合到授权文件           │
│                                                       │
│  SM4密钥 ──→ XOR混淆(与设备ID) ──→ combined_sm4_mac   │
│      │                                                │
│      └────→ SM4加密授权数据 ──→ encrypted_data         │
│                                                       │
│  输出：JSON文件（含以上所有字段）                      │
└─────────────────────────────────────────────────────┘
```

### 4.2 详细步骤

**Step 1 — 构建授权数据（JSON）**

```json
{
  "version": "1.0",
  "issue_date": "2026-01-01T00:00:00",
  "expire_date": "2026-12-31T00:00:00",
  "mac_address": "A1B2C3D4...",
  "extra_data": { }
}
```

注意：`mac_address` 字段在两种模式下含义不同：
- MAC 地址模式：标准 MAC 地址（12位 hex）
- MachineID 模式：64 位十六进制 SHA-256 值

**Step 2 — SM3 哈希计算**

对授权数据的原始 JSON 字节计算 SM3 哈希（32 字节）。

**Step 3 — SM2 签名**

使用 SM2 私钥对 Step 2 的 32 字节哈希值签名，签名 ID 使用 `SM2_DEFAULT_ID`（GmSSL 默认值 `"1234567812345678"`）。

> 设计决策：先哈希后签名，而不是直接对整个授权数据签名。这是密码学上的标准做法，为的是签名效率和对齐标准接口。

**Step 4 — SM4 密钥与设备 ID 绑定**（关键设计）

将 16 字节 SM4 密钥与设备标识符通过 XOR 运算绑定在一起，使得：
- 只有持有正确设备 ID 的一方才能还原出 SM4 密钥
- 授权文件被复制到其他机器后，因设备 ID 不同，还原出的 SM4 密钥错误，无法解密授权数据

绑定算法详见 [第 4.3 节](#43-sm4-密钥与设备-id-绑定算法核心设计)。

**Step 5 — SM4 加密授权数据**

使用 SM4 CBC 模式加密授权数据（JSON 字节），随机生成 16 字节 IV 附加在密文头部。

**Step 6 — 组装授权文件**

所有二进制数据以 Base64 编码嵌入 JSON 结构体。

### 4.3 SM4 密钥与设备 ID 绑定算法（核心设计）

这是整个授权系统中**最核心的防复制机制**。输入 SM4 密钥和设备标识符，输出一个 16 字节的混淆值。

**MAC 地址模式（`USE_MAC_ADDRESS`）：**

设备字节 = MAC 地址标准化后 fromHex（6 字节）
混淆值 = SM4密钥
for i = 0..15:
    混淆值[i] ^= 设备字节[i % 6]   // MAC 循环展开到 16 字节
    混淆值[i] ^= (i + 1)           // 搅乱因子

**机器 ID 模式（`USE_MACHINE_ID`，默认）：**

设备字节 = 64位十六进制 fromHex（32 字节 = SHA-256 输出）
    将 32 字节压缩到 16 字节（前 16 XOR 后 16）
压缩值[i] = 设备字节[i] ^ 设备字节[i + 16]
混淆值 = SM4密钥
for i = 0..15:
    混淆值[i] ^= 压缩值[i]
    混淆值[i] ^= (i + 1)           // 搅乱因子

**提取（反向操作）** 时做同样的 XOR 运算即可恢复原始 SM4 密钥。

> 为什么 XOR 两次：先异或设备 ID，再异或搅乱因子 `(i+1)`。搅乱因子的作用是防止设备 ID 为全零时直接暴露 SM4 密钥。

## 5. 授权码验证流程

> 对应源码：`licensevalidator.cpp` 中的 `validateLicenseFile`

### 5.1 完整验证链路

授权文件(.lic)
    │
    ▼
Step 1 ── JSON 解析 ──→ 检查 format、提取各 Base64 字段
    │
    ▼
Step 2 ── 设备 ID 校验（第一遍） ──→ 比对文件头部 macaddresses 与用户输入的设备 ID
    │
    ▼
Step 3 ── 提取 SM4 密钥 ──→ 从 combined_sm4_mac 和用户设备 ID 反向 XOR
    │
    ▼
Step 4 ── SM4 解密 ──→ 用提取的 SM4 密钥解密 encrypted_data
    │
    ▼
Step 5 ── 解析授权数据 ──→ 得到 version / issue_date / expire_date / mac_address
    │
    ▼
Step 6 ── 设备 ID 校验（第二遍） ──→ 比对解密后数据的 mac_address 与用户输入
    │
    ▼
Step 7 ── SM3 哈希 ──→ 对解密后的授权数据计算 SM3 哈希
    │
    ▼
Step 8 ── SM2 验签 ──→ 用文件中的公钥验证签名（基于 Step 7 的哈希）
    │
    ▼
Step 9 ── 有效期检查 ──→ 当前时间在 issue_date ~ expire_date 之间
    │
    ▼
验证通过 → 填充 ValidatedInfo

### 5.2 关于两次设备 ID 校验（设计说明）

验证流程中有**两处**设备 ID 校验，不是冗余，各有用途：

| 校验点 | 校验对象 | 目的 |
|--------|----------|------|
| Step 2 | 授权文件头部的 `macaddresses` 字段 | **快速失败**：如果头部明文记录的 ID 不匹配，说明文件绑定的是另一台机器，无需进行后续解密运算 |
| Step 6 | 解密后授权数据中的 `mac_address` 字段 | **防篡改**：确认加密数据内部的 ID 与外部声明的一致，防止有人修改头部字段后重放 |

简而言之：Step 2 是前置快速过滤，Step 6 是数据完整性校验。

### 5.3 验证结果

验证通过后返回以下信息：
- `isValid = true`
- 授权版本号、签发日期、过期日期、绑定的设备 ID
- 剩余天数计算
- 状态文本（如"剩余 180 天，有效期共 365 天"）

验证失败时返回具体错误消息，有助于快速定位问题（如"MAC 地址不匹配"、"授权已过期"、"数字签名验证失败"）。

## 6. 授权文件格式

### 6.1 V2 格式完整规范（当前默认）

```json
{
  "format": "SM2_LICENSE_V2",
  "create_time": "2026-01-01T00:00:00",
  "public_key": "<Base64 编码的 SM2 公钥 DER>",
  "signature": "<Base64 编码的 SM2 签名值>",
  "encrypted_data": "<Base64 编码的 SM4 加密数据（含 IV）>",
  "combined_sm4_mac": "<Base64 编码的 SM4+设备ID 混淆值>",
  "macaddresses": "<Base64 编码的设备标识符明文>"
}
```

### 6.2 各字段详解

| 字段 | 解码后长度 | 编码方式 | 说明 |
|------|-----------|----------|------|
| `public_key` | 约 91 字节 | Base64 | SM2 公钥 DER 格式 |
| `signature` | 约 70 字节 | Base64 | SM2 签名（ASN.1 DER） |
| `encrypted_data` | 可变 | Base64 | SM4 CBC 加密：前 16 字节为 IV，后续为密文 |
| `combined_sm4_mac` | 16 字节 | Base64 | SM4 密钥与设备 ID XOR 混淆结果 |
| `macaddresses` | 可变 | Base64 | 设备标识符 UTF-8 字节的 Base64 |

### 6.3 V1 与 V2 差异说明

| 维度 | V1 | V2（当前使用） |
|------|-----|---------------|
| 格式标识 | `SM2_LICENSE_V1` | `SM2_LICENSE_V2` |
| 签名方式 | 直接对原始授权数据签名 | 对 SM3 哈希值签名 |
| 加密触发时机 | V1 内部处理 | V2 显式传参控制 |
| 字段名 | `mac_addresses`（复数） | `macaddresses`（单数） |
| 状态 | 保留兼容性，不再主动生成 | 默认 |

验证器同时兼容 V1 和 V2。新代码应只使用 V2。

### 6.4 文件扩展名

建议使用 `.lic` 作为授权文件扩展名。

## 7. 编译配置与模式切换
> 对应源码：`licensemanager.pro`

### 7.1 两种运行模式

系统提供两套绑定标识方案，通过编译宏切换：

```qmake
# 模式1：使用 MAC 地址（12位十六进制）
#DEFINES += USE_MAC_ADDRESS

# 模式2：使用机器唯一 ID（64位十六进制 SHA-256）— 默认
DEFINES += USE_MACHINE_ID
```

**如何选择：**

| 场景 | 推荐模式 | 理由 |
|------|----------|------|
| 纯内网、硬件环境可控 | MAC 地址 | 简单直接，MAC 地址稳定不变 |
| 公网分发、有虚拟机/容器场景 | 机器唯一 ID | SHA-256 综合多硬件信息，抗干扰更强 |
| 安全要求高 | 机器唯一 ID | 64位十六进制更难猜测和伪造 |

### 7.2 宏影响范围

`USE_MAC_ADDRESS` / `USE_MACHINE_ID` 影响以下文件的行为：

| 文件 | 影响点 |
|------|--------|
| `gmsslcrypto.cpp` | `combineSm4WithMac` / `extractSm4FromCombined` 的绑定算法不同 |
| `licensevalidator.cpp` | 设备 ID 校验逻辑、格式判断不同 |
| `mainwindow.cpp` | UI 标签文本（显示"MAC 地址"还是"机器唯一ID"）、输入验证规则不同 |

### 7.3 DEBUG 宏

```qmake
DEFINES += DEBUG
```

开启后：
- 界面自动填充测试数据
- 日志级别下拉框显示 DEBUG 级别选项
- 生产环境应移除该宏

### 8.3 常见问题排查

| 现象 | 可能原因 | 排查方向 |
|------|----------|----------|
| 授权验证失败：SM4 密钥提取失败 | 设备 ID 输入错误 | 确认验证时输入的 ID 与生成时一致 |
| 授权验证失败：数字签名验证失败 | 公钥不匹配 | 确认验证时使用的公钥与生成时一致 |
| 授权验证失败：数据解密失败 | SM4 密钥损坏或设备 ID 不匹配 | 重新提取 SM4 密钥，检查 combined_sm4_mac 字段 |
| 同一台机器机器码变化 | 硬件变更或 fallback 被重置 | 检查采集组件数，确认是否触发 fallback |
| 机器码为空或过短 | 权限不足 | Windows 检查是否以管理员运行；Linux 检查 DMI 文件权限 |
